| **DESK-RLS-001** | **P1** | Projects | `/projects`, `createProject()`, CSV bulk import | **Creating a project fails for every role**, including Admin and Platform Owner, with a generic "You do not have permission to perform this action." The `projects` table stays permanently empty — nobody has ever been able to create a project through the UI since the RLS scoping migration that introduced this. | `20240101000104_fix_projects_module_rls_scoping.sql` changed `projects_select` to `USING (org_id = current_org_id() AND can_view_project(id))`. `can_view_project(id)` re-queries `projects` **by id** to check ownership/role. `createProject()` does `.insert(...).select('id').single()` — PostgREST's `RETURNING`. Postgres requires a `RETURNING` row to also satisfy the table's own SELECT policy, and a self-referencing subquery like `can_view_project()`'s cannot see a row inserted earlier in the **same command** (standard MVCC command-visibility: a statement's nested subqueries don't see that statement's own inserts). So `can_view_project(id)` always evaluates false for the brand-new row regardless of owner/role, and the whole insert is rejected. Confirmed by direct `psql` reproduction: the identical `INSERT` succeeds with `RETURNING` removed; a **separate**, later statement calling `can_view_project()` on the same row correctly returns `true`; and reducing the WITH CHECK to a bare `true` still failed for the same reason (the failure was never in `projects_insert`'s own check — it was the implicit SELECT-policy re-check `RETURNING` triggers). | New migration `20240101000147_fix_projects_select_returning_visibility.sql`: gives `projects_select` its own inline predicate (`owner_id = auth.uid() OR functional_owner_id = auth.uid() OR created_by = auth.uid() OR EXISTS(...project_members...) OR team match OR role IN (manager/admin/platform_owner)`) instead of routing through `can_view_project(id)`. This has no self-reference, so it sees the new row within the same command. `can_view_project()` itself, and its use by `project_members`/`milestones`/`project_updates`/`project_activity` (which look up an already-committed **parent** project from an earlier statement — never the race), are untouched. | Bisected live in `psql` against the real local Postgres container (`supabase_db_citykart_desk`) with `SET LOCAL role authenticated` + `SET LOCAL request.jwt.claims`, isolating the exact failing clause before writing the fix; re-verified the same reproduction succeeds after the migration; then created a real project end-to-end through the actual UI as the Platform Owner test account ("AUDIT2-20260923-test-project") — succeeded, and `/projects/[id]` rendered correctly. Applied to Local only. | **Fixed** |
| **DESK-TEST-FLAKE-001** *(resolved — was "known, out of scope" in the first pass)* | — | `tests/integration/stage6-channel-readiness.test.ts` + `lib/actions/intake/whatsapp-channel.ts` | `requesterMobileCoverage counts active users with/without a mobile number correctly` failed consistently (`expected +0 to be 1`). | **Genuine query-logic defect**, not a fixture/timing issue. `getWhatsAppChannelReadiness()` computed `activeWithMobile` by fetching every active profile's id (this org has 527+ active users, mirrored from Main) and passing the whole array to `.from('profile_mobile_numbers')...in('profile_id', activeProfileIds)`. PostgREST issues that as a GET request; with 500+ UUIDs the query string exceeds the local Kong gateway's URL-length limit and the request fails with `"URI too long"`. The code destructured only `{ data: mobileRows }` and did `mobileRows ?? []`, so the error was silently swallowed and the coverage count silently went to 0 (or badly undercounted) for **any org large enough to hit the limit** — this affects Main too, not just Local/tests. The test's own hand-rolled ground-truth helper (`countActive()`) had the **identical** `.in()`-over-500-ids pattern using the admin client, so it was *also* silently returning 0 for its "before" baseline — that's why the failure looked like a fixed off-by-one rather than something scaling-dependent. | Rewrote both `getWhatsAppChannelReadiness()` and the test's `countActive()` helper to filter via an embedded PostgREST join (`profile_mobile_numbers.select('profile_id, profiles!inner(is_active)').eq('profiles.is_active', true)`) instead of collecting ids and using `.in()`. No id list is ever built, so there's no URL-length ceiling. | Reproduced the "URI too long" failure directly against the real Postgres/Kong stack with a script mimicking the RLS-scoped client exactly; confirmed the embedded-join query returns correctly and with no error at the same scale; full file now passes 6/6; full suite: **871/871 tests passed, 0 failed, 23 skipped** (previously 870 passed / 1 failed / 23 skipped). | **Fixed** |
