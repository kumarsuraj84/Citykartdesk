# VA-DB: Database security review (RLS, grants, functions, triggers, storage)

Reviewer: VA-DB. Scope: the disposable audit database (`supabase_db_ckdesk_audit`, schema equal to `supabase/migrations/*` up to 163) and the migrations. Method: read-only catalog queries (`pg_policies`, `pg_proc`, `pg_trigger`, `pg_class` ACLs, `has_*_privilege`), plus two read-only role simulations (`BEGIN; SET LOCAL ROLE ...; SELECT count(*) ...; ROLLBACK;` as `anon` and as a synthetic requester/agent/manager/admin). Nothing was written to any database, no file in the repo was changed, nothing outside the local audit container was contacted.

Important context found in the catalog and in the code:

* The portal creates and updates tickets with the **signed-in user's own database client** (`lib/requests/create-request-core.ts:271,474` uses `client` for the insert; `lib/actions/requests.ts:243` updates `assigned_to`/`status` with the user client). So row security and triggers are the real authority; whatever the browser can send to PostgREST (`/rest/v1/...` with the user's JWT) is what the database must defend. Application checks (for example "nobody can change priority") are not a control against a user who skips the app and calls PostgREST directly.
* The audit database has one organization and 336 synthetic profiles (300 user, 24 agent, 5 manager, 5 admin, 2 platform_owner), so every cross-organization item below is proven by reading the policy text, not by running two tenants.
* Earlier audit IDs are re-verified in section 2 (D-002, D-003, D-004, D-006, D-007, D-008, D-023).

---

## 1. Candidate vulnerabilities

### VA-DB-01  High  Direct PostgREST UPDATE on `requests` still lets a technician or manager change priority, SLA due dates, assignee and other lifecycle columns; SLA tampering is not even logged

* **Module:** requests table, trigger `guard_request_client_write`, policy `requests_update`, audit trigger.
* **Severity reason:** breaks the stated business rule (priority and SLA cannot be changed by hand) for any technician or manager with a valid login; low skill (one HTTP call); also hides the evidence for SLA dates.
* **Evidence:**
  * Policy `requests_update` (catalog): `USING (org_id = current_org_id() AND (team_id = ANY(current_user_team_ids()) OR current_user_role() IN ('manager','admin','platform_owner')))`, `WITH CHECK (request_identity_unchanged(id, org_id, requester_id, service_id, team_id) AND (team member OR manager/admin/platform_owner))`. Only org, requester, **service** and team are frozen. (So service change IS blocked at database level, which is good. Priority is not.)
  * Trigger `trg_guard_request_client_write` (`supabase/migrations/20240101000163_request_status_transitions.sql:29-52`, earlier `20240101000157_post_audit_high_security.sql:109-137`). The `UPDATE` branch only checks: `request_no`/`created_at` unchanged, and `status` transition allowed. The "SLA dates / priority / assigned_to" checks exist only in the `INSERT` branch.
  * `authenticated` has table-wide `UPDATE` on `requests` (all 33 columns; only `profiles` has column-level grants: `pg_attribute.attacl`).
  * Audit trigger `trg_system_log_audit` on `requests` watches only `status,assigned_to,priority,team_id,requester_id,service_id,resolved_at,closed_at,reopen_count`. `response_due_at`, `resolution_due_at`, `waiting_since`, `paused_ms_total`, `responded_at`, `reopen_deadline_at`, `form_data` are not watched; an update that changes only those writes **no** `system_log` row (`system_log_audit_trigger` returns early when `v_changed` is empty).
  * Application rule being bypassed: `lib/actions/requests.ts:876-878` ("no role... can override it") and `tests/unit/no-priority-change.test.ts`. Those only remove the buttons; there is no database constraint.
* **Plain-language explanation:** The app no longer shows a "change priority" button, but the database itself still accepts that change. Any technician in the ticket's team, or any manager/admin, can send the change straight to the database service and set a ticket to low priority, move its due date a year ahead, or assign it to someone who is not on the team. Changes to the due dates leave no trace in the System Log, so a missed SLA can be hidden.
* **Exploit scenario (technician in team T, or any manager):** As PostgREST would run it:
  ```
  BEGIN;
  SET LOCAL ROLE authenticated;
  SELECT set_config('request.jwt.claims','{"sub":"<technician uuid>","role":"authenticated"}',true);
  UPDATE requests
     SET priority = 'low',
         resolution_due_at = now() + interval '365 days',
         response_due_at   = now() + interval '365 days',
         assigned_to       = '<any profile uuid>',
         paused_ms_total   = 999999999
   WHERE id = '<ticket in team T>';
  ```
  HTTP form: `PATCH /rest/v1/requests?id=eq.<id>` with `apikey`, `Authorization: Bearer <technician JWT>`, `Content-Type: application/json`, body `{"priority":"low","resolution_due_at":"2027-12-31T00:00:00Z"}`. Expected today: success, 1 row; `system_log` gets a row for `priority` and `assigned_to` but none for a dates-only change. Other writable columns in the same call: `resolved_at`, `closed_at` (with no status change), `reopen_count`, `reopen_deadline_at`, `waiting_since`, `responded_at`, `category_id`, `sub_category_id`, `parent_request_id`, `project_id`, `cancellation_reason`, `pre_approval_status`, `form_data`, `source_metadata`. Status is limited to the allowed pairs, but with no rule that a resolution note exists (`in_progress -> resolved` or `waiting_user -> resolved` with no comment is accepted).
* **Prove locally:** On the audit stack, sign in as a synthetic agent (fixtures in `tests/setup/fixtures.ts`) who is in team T, call the PATCH above for a ticket of team T inside a transaction you roll back (or on a throw-away copy), expect 1 row updated and `priority` changed. Then run the same as a requester with no team: expect 0 rows (RLS). Check `SELECT * FROM system_log WHERE entity_id='<id>' ORDER BY id DESC` to see no row for the dates-only call.
* **Suggested minimal fix:** (a) Same technique already used for `profiles` (migration 156): `REVOKE UPDATE ON public.requests FROM authenticated; GRANT UPDATE (<only the columns the app really writes with the user client: status, assigned_to, responded_at, ...>) ON public.requests TO authenticated;` and move everything else (priority, due dates, resolved/closed times, reopen fields) to the service client or to a `SECURITY DEFINER` function. (b) In the `UPDATE` branch of `guard_request_client_write` also reject changes to `priority`, `response_due_at`, `resolution_due_at`, `paused_ms_total`, `waiting_since`, `reopen_count`, `closed_at`, `resolved_at` unless `current_user` is not `authenticated`/`anon`, and require `assigned_to` to be a member of the request's team. (c) Add the due-date and pause columns to the watch list of `trg_system_log_audit`.
* **Confidence:** CONFIRMED-BY-CODE (policy text, trigger body and ACLs read from the live catalog). The write itself was not executed (read-only rule).

### VA-DB-02  Medium  Any signed-in user can INSERT a ticket straight into `requests` with a free choice of priority, service, team, category and project, skipping every application rule

* **Module:** `requests` INSERT policy and `guard_request_client_write` INSERT branch.
* **Severity reason:** the creation rules (mandatory form, priority from sub-category, SLA, routing) are app-only; effect is on ticket integrity and queue noise, not on other people's data.
* **Evidence:** policy `requests_insert`: `WITH CHECK ((requester_id = auth.uid()) AND (org_id = current_org_id()))`. The INSERT branch of the guard only demands `status IN ('open','pending_approval')`, no assignee, no SLA dates, no resolved/closed times, zero pause/reopen counters. Nothing checks that `service_id`, `team_id`, `category_id`, `sub_category_id`, `project_id`, `parent_request_id`, `intake_message_id` belong to the caller's organization or to each other, nothing recomputes `priority`, nothing validates `form_data` against the service form. `request_identity_unchanged()` is applied on UPDATE only. Foreign keys do not carry `org_id`.
* **Plain-language explanation:** A normal employee who knows how to call the database service can create a ticket that did not go through the request form: pick "urgent" priority, send it to any team queue (even a team of another organization), skip the mandatory questions, and the ticket gets no due dates at all, so no SLA clock ever runs on it.
* **Exploit scenario:** Requester R: `POST /rest/v1/requests` body `{"title":"x","description":"y","requester_id":"<R>","org_id":"<R's org>","service_id":"<any service uuid, any org>","team_id":"<any team uuid, any org>","priority":"urgent","status":"open","form_data":{},"source_metadata":{"created_via":"portal"}}`. Expected today: 201. Result: ticket with chosen priority, no `response_due_at`/`resolution_due_at`, routed to the chosen team (if the team belongs to another organization nobody there can see it, but the organization's managers and the requester can; it pollutes reports).
* **Prove locally:** requester JWT from fixtures, the POST above, expect 201 with `priority = urgent`; then `SELECT team_id, service_id FROM requests WHERE id=...` shows the foreign values.
* **Suggested minimal fix:** add a `BEFORE INSERT` trigger (client roles only) that: sets `priority` from the sub-category / service default (same function the app uses), fills `team_id` from `services.team_id` (rejects mismatch), checks service/team/category/sub-category/project have `org_id = NEW.org_id`, and stamps SLA dates itself. Or make portal creation use the service client (the way Email Intake already does with `useAdminForWrites`) and `REVOKE INSERT ON requests FROM authenticated`.
* **Confidence:** CONFIRMED-BY-CODE.

### VA-DB-03  Medium  Database lets `manager` write configuration the application reserves for `admin` (services, SLA policies, SLA config, many master tables), and gives managers org-wide read of every ticket

* **Module:** policies `services_admin`, `sla_policies_admin`, `global_sla_config` (`sla_config_admin`), `field_sla_overrides_write`, `form_templates_admin`, `form_field_library_admin`, `categories_admin`, `loc_admin`, `dept_admin`, `designations_admin`, `job_functions_admin`, `cc_admin`, `stores_admin`, `oems_admin`, `assignment_rules` (`rules_admin`), `notification_rules_admin`, `alert_rules_admin`, `approval_workflows`/`approval_workflow_steps` (manager allowed by app too), `team_members_*` insert/delete (manager).
* **Severity reason:** privilege gap between the role in the app and the role in the database; needs a manager account (only 5 of 336 in the audit data), impact is configuration tampering (for example lengthening every SLA).
* **Evidence:** `services_admin ... FOR ALL ... current_user_role() = ANY (admin, manager, platform_owner)`; `lib/actions/admin/services.ts:18` and `lib/actions/admin/sla-policies.ts:18` only allow `admin`/`platform_owner`. `authenticated` has table-level INSERT/UPDATE/DELETE on all of these tables (`has_table_privilege`). The permission matrix (`permission_overrides`) is a UI setting that no policy reads, so switching a permission off for managers does not stop the database from letting them write. `requests_select` has `current_user_role() = ANY (manager, admin, platform_owner)` with no team or direct-report limit (simulated: a manager that belongs to one team reads all 3000 requests, 3002 activity rows and 2402 comments; an agent reads only the 462 of his team).
* **Plain-language explanation:** In the screens only an Administrator can edit services and SLA policies, but the database accepts the same edit from any Manager. A manager (or anyone who steals a manager login) can therefore change how fast tickets are due for the whole company, or rewire the services, using the database service directly. Managers also see every ticket in the company, not only their team's or their direct reports'.
* **Exploit scenario:** Manager M: `PATCH /rest/v1/sla_policies?org_id=eq.<org>` body `{"config":{...long hours...}}` or `PATCH /rest/v1/global_sla_config?org_id=eq.<org>&priority=eq.urgent` body `{"resolution_hours":9999}`. Expected today: rows updated; audit rows are written (trigger on these tables) so it is detectable, not preventable.
* **Prove locally:** manager JWT from fixtures, PATCH above, expect success; the same call as an agent or requester expects 0 rows.
* **Suggested minimal fix:** align policies to the app: change the role lists on `services`, `sla_policies`, `global_sla_config`, `field_sla_overrides`, `categories`, `sub-categories`, `stores`, `oems` etc. to `admin, platform_owner` where the app is admin-only; for tables the app does not write with the user client at all (check each), `REVOKE INSERT, UPDATE, DELETE` from `authenticated` and let the service client write. Decide explicitly whether manager read should be limited to teams and direct reports (product decision; today it is org-wide).
* **Confidence:** CONFIRMED-BY-CODE for the write gap; the read scope is by design in policy text (record as a decision).

### VA-DB-04  Medium  A user can switch off their own "must reset password" flag without changing the password

* **Module:** `profiles` column grant + `guard_profile_client_update`.
* **Evidence:** `GRANT UPDATE (full_name, avatar_url, must_reset_password) ON public.profiles TO authenticated` (migration 156:83; catalog confirms `attacl` on exactly those three columns). The guard only blocks setting it to TRUE (`OR (NEW.must_reset_password IS DISTINCT FROM OLD.must_reset_password AND NEW.must_reset_password IS TRUE)`). The only place that enforces the reset is `app/(app)/layout.tsx:37` (a page-render redirect); `lib/actions/auth.ts:102-103` clears it with the user client after the password change.
* **Plain-language explanation:** Accounts created with a starting password are meant to force the person to choose their own password at first login. The person (or anybody who learned the starting password) can simply tell the database "reset not needed" and carry on using the starting password forever.
* **Exploit scenario:** user with flag true signs in with the starting password, then `PATCH /rest/v1/profiles?id=eq.<own uuid>` body `{"must_reset_password":false}` -> 204; the layout redirect no longer triggers. Relevant to open item D-011 (bulk-import default password).
* **Prove locally:** create a profile with `must_reset_password=true` via fixtures, sign in as it, PATCH as above, reload any app page: no forced reset.
* **Suggested minimal fix:** drop `must_reset_password` from the user column grant and clear it only from the server (service client) after `updateUser({password})` succeeded; also make the server (not only the layout) refuse server actions while the flag is true.
* **Confidence:** CONFIRMED-BY-CODE.

### VA-DB-05  Medium  `task-attachments` bucket: any signed-in user can upload any file into it, and file rows (and therefore download rights) can be forged

* **Module:** storage policies `task_attach_storage_insert`, `task_attach_storage_select`; table `task_attachments` policy `task_attachments_insert`.
* **Evidence:**
  * `task_attach_storage_insert` (`20240101000080_rls_hardening_cross_tenant.sql:413-414`): `WITH CHECK (bucket_id = 'task-attachments' AND auth.uid() IS NOT NULL)`, role `public`. No path rule, no task rule.
  * The app uploads with the **service client** and records the row with the service client (`lib/actions/task-attachments.ts:62-92`), so neither user-level policy is needed. The app's magic-byte check (`validateAttachment`, line 40) is skipped by a direct Storage API upload.
  * `task_attach_storage_select` grants read of an object when a `task_attachments` row with the same `storage_path` is on a task the caller can see. `task_attachments_insert` lets the caller insert such a row for any task they created, with a free `storage_path` (there is no guard trigger like `guard_attachment_client_write`). So a user can create a task, add a row whose `storage_path` equals another task's file path, and then read that file.
* **Plain-language explanation:** Any employee can put files (up to 25 MB each, no quota) into the task file store without going through the app's checks, and can create a "file record" pointing at somebody else's file to get permission to open it. The second part needs the exact file path (it starts with a long random task id), so it is hard to use, but the first part is open.
* **Exploit scenario:** (1) `POST /storage/v1/object/task-attachments/<anything>` with a requester JWT -> 200 (uploads unvalidated content; SVG/zip are on the allowed type list). (2) as task owner: `POST /rest/v1/task_attachments {"task_id":"<mine>","uploaded_by":"<me>","file_name":"x","storage_path":"<victim_task_id>/<ts>-<name>"}` then `GET /storage/v1/object/authenticated/task-attachments/<that path>`.
* **Prove locally:** with a fixture user JWT upload a small text file to a random name in `task-attachments` and expect 200; (2) needs two tasks in the fixtures.
* **Suggested minimal fix:** `DROP POLICY task_attach_storage_insert` (and `task_attach_storage_select`/`delete` if downloads are via signed URLs made by the service client); `REVOKE INSERT, UPDATE, DELETE ON task_attachments FROM authenticated` or add the same path guard as for `request_attachments` (`storage_path LIKE task_id || '/%'`).
* **Confidence:** CONFIRMED-BY-CODE for the open upload; PLAUSIBLE for the forged-row read (needs a known path).

### VA-DB-06  Medium (Low if only one organization is ever hosted)  `request-attachments` read policy ignores the organization for managers/admins and ignores the "internal" flag; several INSERT policies have a role branch with no organization test

* **Module:** `storage.objects` policy `storage_request_attachments_select`; table policies `request_comments_insert`, `request_attachments_insert`.
* **Evidence:**
  * `storage_request_attachments_select` (catalog; original `20240101000003_attachments.sql:123`): `EXISTS (SELECT 1 FROM request_attachments ra WHERE ra.storage_path = objects.name AND ra.deleted_at IS NULL AND EXISTS (SELECT 1 FROM requests r WHERE r.id = ra.request_id AND (r.requester_id = auth.uid() OR is_team_member(r.team_id) OR current_user_role() IN ('manager','admin'))))`. There is no `r.org_id = current_org_id()` and no `ra.is_internal = false` for the requester branch.
  * `request_comments_insert` and `request_attachments_insert` (`WITH CHECK ... (r.requester_id = auth.uid() OR is_team_member(r.team_id) OR current_user_role() IN ('manager','admin','platform_owner') OR is_request_collaborator(r.id))`): the role branch does not require the ticket to be in the caller's organization.
  * `20240101000157_post_audit_high_security.sql:3-11` states that the app downloads with its service client, so this user-level read policy is not needed by the application (D-004 dropped only the broader "Authenticated download only" and the insert policy).
* **Plain-language explanation:** A manager or administrator of one organization could list and open the attachment files of another organization's tickets (and add comments or attachment records to them) if they know or can list the file paths; and an attachment marked "internal" is still downloadable by the requester of that ticket straight from the file store. In today's single-company installation the first part has no practical effect; the second one is latent because the app currently never creates an internal attachment (`lib/actions/attachments.ts:161` sets `is_internal:false`), but a requester can insert one himself.
* **Exploit scenario:** manager of org A: `POST /storage/v1/object/list/request-attachments {"prefix":"","limit":100}` returns objects of every organization (the policy has no org test); then GET each object. Requester: insert a `request_attachments` row with `is_internal=true` for own ticket, then list the folder through Storage: the object is listed.
* **Prove locally:** needs a second organization in the audit data; for the internal case, a fixture requester can do it on one org.
* **Suggested minimal fix:** drop the user-level storage SELECT policy (the app uses signed URLs from the service client); otherwise add `r.org_id = current_org_id()` and `(ra.is_internal = false OR is_team_member(r.team_id) OR role in manager/admin)`. Add `r.org_id = current_org_id()` to the manager/admin branch of `request_comments_insert` and `request_attachments_insert`.
* **Confidence:** CONFIRMED-BY-CODE.

### VA-DB-07  Medium  Every signed-in requester can read org-wide personal and configuration data (mobile numbers, full employee list with roles, who the technicians are, escalation and alert rules)

* **Module:** SELECT policies with only `org_id = current_org_id()`: `profile_mobile_numbers_select` (`org_id = current_org_id() OR profile_id = auth.uid()`), `profiles_select`, `team_members_select`, `alert_rules_select`, `escalation_policies_select`, `approval_workflows`/`approval_workflow_steps` select, `saved_reports_select`, `scheduled_reports_select` (recipients and filters), `related_requests_select`, `permission_overrides_select`, `global_sla_config`, `stores` (200 rows with AC/vendor data), `organizations`.
* **Evidence:** simulated as a requester with no team and no tickets (`e1d14aed...`, role `user`): readable tables with rows = `profiles=336`, `team_members=25`, `approval_workflows=418`, `alert_rules=4`, `stores=200`, `global_sla_config=4`, `sla_policies=4`, ... Policy text for the empty tables (`profile_mobile_numbers`, `saved_reports`, `scheduled_reports`, `related_requests` had 0 rows in the audit data) is org-wide for any role.
* **Plain-language explanation:** Any of the ~300 ordinary employees can download the list of all colleagues with job role, manager, employee id and (once loaded) mobile phone numbers, which technicians belong to which team, and the internal alert/escalation rules. Mobile numbers are personal data and requesters have no business reading them.
* **Exploit scenario:** requester JWT: `GET /rest/v1/profile_mobile_numbers?select=*` and `GET /rest/v1/profiles?select=id,full_name,role,employee_id,manager_id,store_id`.
* **Prove locally:** populate one `profile_mobile_numbers` row, read it as `e1d14aed...` (simulation above).
* **Suggested minimal fix:** `profile_mobile_numbers_select` -> own row or manager/admin only; `saved_reports_select`/`scheduled_reports_select` -> creator or manager/admin; consider a column-restricted view or column grants for `profiles` (hide `employee_id`, `manager_id`, `role` from role `user`); restrict `alert_rules`, `escalation_policies`, `approval_workflows` to staff roles.
* **Confidence:** CONFIRMED-BY-CODE (profiles/team_members/approval_workflows/alert_rules simulated; the rest from policy text).

### VA-DB-08  Medium if sign-up is enabled in production (Low otherwise)  `handle_new_user()` puts every new auth account into the oldest organization; sign-up is enabled in the repo's local config

* **Module:** trigger `on_auth_user_created` -> `handle_new_user()` (SECURITY DEFINER); `supabase/config.toml:176,221`.
* **Evidence:** `INSERT INTO public.profiles (id, full_name, avatar_url, org_id) VALUES (NEW.id, ..., (SELECT id FROM organizations ORDER BY created_at ASC, id ASC LIMIT 1))`, role defaults to `user`. `config.toml`: `enable_signup = true`, `enable_confirmations = false`. The production template `deploy/windows/config/auth.env.example:51` sets `GOTRUE_DISABLE_SIGNUP="true"` (good), but `GOTRUE_MAILER_AUTOCONFIRM="true"` is also set.
* **Plain-language explanation:** If the login service allows self-registration, anyone holding the public API key (it is in every web page) can create an account and automatically becomes an employee of the first company, able to read the staff list (VA-DB-07), create tickets (VA-DB-02) and so on. The production template turns self-registration off; this needs to be verified on the live auth service, and the local stack default is "on".
* **Exploit scenario:** `POST /auth/v1/signup {"email":"x@example.com","password":"..."}` with the anon key; then sign in and call the requester queries in VA-DB-07.
* **Prove locally:** against the audit auth container (`/auth/v1/signup` through the local Kong), expect a session and a new `profiles` row in org `...0001`; the infra reviewer should confirm `GOTRUE_DISABLE_SIGNUP` on 10.0.1.98 (not touched here).
* **Suggested minimal fix:** keep `GOTRUE_DISABLE_SIGNUP=true` in production and `enable_signup = false` in `config.toml`; make `handle_new_user` create the profile as inactive (`is_active=false`) or with `org_id NULL` until an administrator activates it.
* **Confidence:** PLAUSIBLE (depends on the running auth configuration).

### VA-DB-09  Low  `get_home_dashboard` trusts caller-supplied role flags and counts approvals across organizations; it also returns the ticket number of any linked ticket

* **Module:** `get_home_dashboard(p_is_manager, p_is_agent, p_team_id, p_has_tasks)`, SECURITY DEFINER, executable by `anon` and `authenticated`.
* **Evidence:** the `pending_approvals` count is `FROM approvals a JOIN approval_workflow_steps aws ON ... WHERE a.status='pending' AND (aws.approver_user_id = v_uid OR (aws.approver_type = 'any_manager' AND p_is_manager))` with no `org_id` condition and `p_is_manager` taken from the caller; the `tasks_*` branches select `request_no FROM requests r WHERE r.id = t.request_id` without any visibility test, and `tasks_insert` lets any user create a task with any `request_id`. `p_team_id` is not used.
* **Plain-language explanation:** A requester can call the dashboard function and tell it "I am a manager"; the answer then includes how many "any manager" approvals are waiting in the whole database (all organizations). A requester can also link a personal task to any ticket id and the dashboard shows that ticket's number. These are small leaks (counts and a ticket number), not content.
* **Exploit scenario:** `POST /rest/v1/rpc/get_home_dashboard {"p_is_manager":true,"p_is_agent":true}`; for the number: create task with `request_id=<foreign id>` assigned to self, call the function.
* **Suggested minimal fix:** derive manager/agent from `current_user_role()` inside the function, add `AND r.org_id = v_org_id` (and org to the approvals join), and revoke EXECUTE from `anon`.
* **Confidence:** CONFIRMED-BY-CODE.

### VA-DB-10  Low  Several write policies check only the organization, so a low-privilege user can alter rows he does not own

* **Module / evidence (each from the policy text):**
  * `intake_reviews_update` (agent+ in org, table `UPDATE` granted, 33 columns): any technician can change any review's `state`, `reviewed_by`, `final_priority`, `created_request_id`, `assigned_reviewer_id` (forge who reviewed, mark done, point at another ticket). No state-transition trigger exists.
  * `intake_notes_org_write` INSERT: any role (including a plain requester) in the organization, `author_id` not checked (forge note author). (Table INSERT is actually not granted to `authenticated` for `intake_notes`, so this policy is inert today.)
  * `project_members_insert/delete`, `project_updates_insert`: any technician can add himself (or anyone) to any project in the org by id, which makes the project visible to him (`projects_select`/`can_view_project` include membership), and can delete anyone's membership.
  * `tasks_insert`: any role incl. requester can create tasks assigned to any `assignee_id`/`team_id`/`request_id`/`project_id` (noise, VA-DB-09).
  * `request_time_entries_update` (`user_id = auth.uid()`, no WITH CHECK on `request_id`), `csat_update_requester` (requester can change `request_id` and `rating` while `submitted_at IS NULL`): rows can be re-pointed at other tickets.
  * `request_attachments` guard (`guard_attachment_client_write`) freezes path, size, type, uploader and request but not `is_internal`, `deleted_at` (an uploader can restore a deleted file), `comment_id`, `uploaded_at`.
  * `profiles_update_own` + column grant lets anyone rename himself (`full_name`) to any text, including another person's name, with no uniqueness (impersonation in the conversation list; the audit log still records the real actor id).
* **Plain-language explanation:** A number of "small" tables trust the user to send honest ids and flags. None of them exposes ticket content, but they allow forging who reviewed an e-mail, joining projects uninvited, posting a satisfaction rating onto the wrong ticket, or restoring a deleted file.
* **Suggested minimal fix:** per table, add `WITH CHECK` on the parent key (`EXISTS (... same org and caller allowed ...)`), freeze identity columns by trigger, and for `intake_reviews` grant only the columns/transitions the review screen needs. Also `REVOKE INSERT/UPDATE` on tables the app writes only with the service client.
* **Confidence:** CONFIRMED-BY-CODE (policy text and grants); exploitation of each is simple but each has low impact.

### VA-DB-11  Low  Approval e-mail code: the wrong-guess counter can be raced

* **Module:** `lib/approvals/email-code.ts:28-45` (the table `approval_email_codes` itself is correctly locked, see section 2).
* **Evidence:** a wrong guess reads `attempts = k`, then runs `UPDATE ... SET attempts = k+1 WHERE id = ... AND attempts = k` and returns `wrong` whether or not that update changed a row. Parallel guesses that all read `k` get `wrong` for free; only one of them advances the counter. `hashApprovalCode` falls back to an empty HMAC key when the secret is not set (`lib/approvals/email-link.ts:91`).
* **Plain-language explanation:** The six-digit code allows five wrong tries, but if an attacker sends hundreds of guesses at the same instant they are counted as one try. The attacker also needs the signed link from the approver's e-mail, and gets only about five bursts, so the chance of success is small (about 5 x burst size out of 1,000,000).
* **Suggested minimal fix:** increment atomically in one SQL statement (`UPDATE ... SET attempts = attempts + 1 ... RETURNING attempts`) before comparing, fail closed when `secret()` is empty.
* **Confidence:** CONFIRMED-BY-CODE (race); success probability is low.

### VA-DB-12  Low (hardening)  Excess grants and defaults that are not reachable through PostgREST today but remove all defence if any SQL path appears

* `TRUNCATE`, `TRIGGER`, `REFERENCES` are granted to `authenticated` on 99 of 106 `public` tables and to `anon` on 91 (`has_table_privilege`). `TRUNCATE` ignores row security. `anon` also has INSERT/UPDATE/DELETE on 18 tables (`alert_rules, assignment_rules, cost_centers, departments, global_sla_config, locations, request_attachments, request_time_entries, scheduled_reports, service_sub_categories, sla_escalation_events, task_activity, task_assignees, task_comments, task_custom_field_values, task_custom_fields, task_template_items, task_templates`); today every policy fails for `anon` (`auth.uid()` is null; verified by the `anon` simulation: zero readable rows in any table, and a scan found no policy applying to `anon` that is true without `auth.uid()`/`current_*`).
* Default privileges (`pg_default_acl`): new tables created by `postgres` in `public` get `Dxtm` (TRUNCATE/REFERENCES/TRIGGER/MAINTAIN) for `anon`, `authenticated`; new sequences get `w`; new functions in `public` keep the PostgreSQL default `EXECUTE` for `PUBLIC`.
* Sequences `system_log_id_seq`, `app_event_log_id_seq`: `UPDATE` (nextval/setval) granted to `authenticated`.
* `net` schema (`pg_net`): `net.http_get/http_post/http_delete` executable by `anon` and `authenticated`, `net.http_request_queue` and `net._http_response` readable by `anon`; `extensions.pg_stat_statements` readable by `anon`/`authenticated`; `supabase_functions.hooks`/`migrations` readable; `realtime.send` executable. None of these schemas is exposed by PostgREST (`config.toml: schemas = ["public","graphql_public"]`, production `postgrest.conf.example: db-schemas = "public"`), so they are only reachable through a SQL injection or a database login. `graphql_public.graphql` is executable by `anon` (schema introspection on the local stack).
* SECURITY DEFINER helpers executable by `anon`: `request_identity_unchanged(id, org, requester, service, team)` is a yes/no oracle about any ticket id (needs the id), `can_view_project`, `is_*`, `current_*`, `get_enabled_modules`, `has_module_access` (all scoped to `auth.uid()`; harmless for `anon`).
* No table has `FORCE ROW LEVEL SECURITY` (the owner `postgres` bypasses anyway; it only matters if a table owner ever becomes the API role).
* Production `postgrest.conf.example` has no `db-max-rows` (the local config sets `max_rows = 1000`) and PostgREST serves an OpenAPI schema to `anon`.
* **Suggested minimal fix:** `REVOKE TRUNCATE, TRIGGER, REFERENCES ON ALL TABLES IN SCHEMA public FROM anon, authenticated;` `REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon;` (re-grant SELECT only where a public page needs it; none seems to), `ALTER DEFAULT PRIVILEGES ... REVOKE ... FROM anon, authenticated` and `REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`, `REVOKE EXECUTE ON FUNCTION public.request_identity_unchanged(...) FROM anon`, set `db-max-rows` and disable OpenAPI for `anon` in production.
* **Confidence:** CONFIRMED-BY-CODE (grants), no direct exploit found.

## 2. Controls verified as sound (and earlier audit items re-verified)

* **RLS coverage:** all 106 `public` base tables have RLS enabled; 8 of them (`approval_email_codes`, `system_log_archive`, `app_event_log`, `email_smtp_settings`, `org_signup_requests`, `processed_inbound_emails`, `conversation_events`, `conversation_attachments`) have zero policies and no `authenticated`/`anon` privileges (deny all). The only table with RLS off, `system_log_chain_head`, has no grants for `anon`/`authenticated` (`has_table_privilege` false for all verbs). No views or materialized views in `public`, so no `security_invoker` issue.
* **Anonymous access:** as `anon`, a loop over every table returned zero rows (no `NOTICE` lines with counts). No `public` policy is true without `auth.uid()`/`current_*` except the intended `RESTRICTIVE ... false` insert blocks (`admin_audit_no_insert`, `intake_audit_no_insert`, `business_rule_events_no_insert`, `approval*_insert_deny`, `request_activity_insert_deny`, `task_activity_insert_deny`) and `request_sequences_no_direct_access`. D-006 verified fixed in effect (global config tables have `authenticated` read, `platform_owner` write only).
* **Profiles self-promotion (D-003 verified):** `authenticated` has `UPDATE` only on `full_name, avatar_url, must_reset_password` (`pg_attribute.attacl`); the BEFORE UPDATE trigger `trg_guard_profile_client_update` (`20240101000156...:87`) rejects changes to id/org/role/is_active/manager/store/department/location/cost_center/function/designation/employee_id/job_title/whatsapp_enabled; `profiles_update_own` also locks `role`; no INSERT or DELETE policy exists. `team_members` insert/delete require manager/admin/platform_owner in the same org. Role cannot be self-promoted; `manager_id` (which drives `current_user_subordinate_ids()` visibility) cannot be self-set.
* **Isolation of tickets for requesters:** `requests_select`, `comments_select`, `request_activity_select`, `approvals_select`, `request_attachments_select` all start with `org_id = current_org_id()` and limit non-staff to own tickets; internal comments hidden from requesters (`NOT is_internal OR manager/admin OR ticket team OR (collaborator AND is_agent)`). Simulated requester sees none of `requests`, `request_comments`, `tasks`, `notifications`. Deactivated users lose access in the database (`current_org_id()`/`current_user_role()` require `is_active`; D-010).
* **Request identity frozen on update:** `request_identity_unchanged()` in the WITH CHECK freezes `org_id, requester_id, service_id, team_id` (service change really is impossible via PostgREST). `request_no` and `created_at` frozen by `guard_request_client_write`. D-008 (INSERT side: status, assignee, SLA dates, resolved/closed times, counters) verified; the UPDATE side is incomplete (VA-DB-01).
* **Status transitions (D-023 closed locally):** `request_status_transition_allowed()` (migration 163) is enforced for `authenticated`/`anon`; `closed` is unreachable from the user client, `pending_approval` has no way out through the client, `cancelled`/`closed` are terminal. `approvals`, `approval_decisions`, `request_activity` cannot be inserted/updated by users (restrictive INSERT deny and no UPDATE policy). `request_comments` cannot be updated or deleted (no UPDATE policy; DELETE policy `false`).
* **Audit and System Log immutability:** `authenticated` has only `SELECT` on `system_log` (INSERT/UPDATE/DELETE/TRUNCATE false), `system_log_archive` has no privileges; BEFORE UPDATE/DELETE/TRUNCATE triggers `system_log_guard` raise except the `citykart.system_log_archive` flag set inside `system_log_archive_old()` (which only roles with DELETE could use); hash chain `system_log_chain` + `system_log_verify_chain` (EXECUTE revoked from users). The actor is taken from `auth.uid()`; the `x-actor-id` header is trusted only when the JWT role is `service_role` (a user JWT cannot claim that). `system_log_clean` redacts password/secret/token/key/credential/otp/code_hash keys. `admin_audit_log`, `intake_audit_log`, `business_rule_events` cannot be written by users. `owner_audit_log` has no INSERT grant.
* **SECURITY DEFINER functions (39):** all 39 have `search_path` pinned (`public` or `public, vault`; none unpinned). The only function with dynamic SQL is `owner_delete_org` (`EXECUTE format('DELETE FROM public.%I WHERE org_id = $1', r.table_name) USING p_org_id`): identifiers come from `information_schema` and are quoted with `%I`, the id is bound; EXECUTE is revoked from PUBLIC/anon/authenticated and it re-checks `is_owner_org()` (D-002 verified). Revoked from users (only `service_role`): `owner_delete_org`, `replace_user_email`, `purge_app_event_log`, `generate_request_no`, `seed_default_sla_config`, `trg_assign_request_no`, `trg_seed_org_sla_config`, `upsert_field_sla_override`, `system_log_archive_old`, `system_log_verify_chain`, `commit_conversation_transition`, `email_smtp_*`, `intake_read/store_credential`, `org_read/store_desktime_key`, `merge_request_form_data` (D-007 verified). `replace_user_email` builds its regex by escaping metacharacters and every statement is scoped by `p_org_id` (callable only by the server). Vault secrets are unreachable by users (`vault` schema has no USAGE for `anon`/`authenticated`).
* **Helper functions callable by users** (`current_org_id`, `current_user_role`, `current_user_team_ids`, `current_user_subordinate_ids`, `is_team_member`, `is_agent`, `is_owner_org`, `can_view_project`, `can_manage_collaborators`, `is_request_approver/collaborator`, `get_enabled_modules`, `has_module_access`) are keyed on `auth.uid()` and return nothing useful for another user; the others take an id but only answer about the caller.
* **Approval e-mail codes (`approval_email_codes`):** `REVOKE ALL ... FROM PUBLIC, anon, authenticated`, RLS on with no policies, `code_hash` is an HMAC keyed by the server secret; codes are random (`randomInt`), 10-minute expiry, single use claimed atomically (`used_at IS NULL` update). Only the attempt counter race is open (VA-DB-11).
* **Storage:** `request-attachments`, `task-attachments`, `intake-attachments` are private (`public=false`), 25 MB limit and a mime allow-list on each; `icons` is the only public bucket (5 MB, image types, no user INSERT policy). `request-attachments` INSERT only for `service_role`; no UPDATE policies on `storage.objects` (no overwrite); `request_attachments` rows must have `storage_path LIKE request_id || '/%'` and not contain `..` (`guard_attachment_client_write`), so a user cannot attach another ticket's file to his own ticket.
* **Roles and engine settings:** `postgres` is not a superuser; `anon` statement_timeout 3s, `authenticated` 8s, `authenticator` lock_timeout 8s; `row_security = on`; `authenticated`/`anon` are not members of any privileged role; no `dblink`, `http`, `file_fdw`, `pg_cron` extension installed (`pg_net`, `pgcrypto`, `pg_trgm`, `uuid-ossp`, `supabase_vault`, `pg_stat_statements` only); `CREATE` on schema `public` is denied to both roles; `pg_read_file`/`pg_ls_dir` not executable by `authenticated`. No Realtime publication exists and `realtime.messages` has RLS with no policies.
* **Production templates:** `deploy/windows/config/auth.env.example:51` `GOTRUE_DISABLE_SIGNUP="true"`; `postgrest.conf.example` exposes only `public`.
* **Application-level checks backed by the database:** scheduled-report recipients are re-validated at send time (`lib/actions/admin/reports.ts:202`), so a manager writing rows directly through `scheduled_reports_admin` (policy allows manager) cannot make the server mail the report outside the organization (defence in depth only).
