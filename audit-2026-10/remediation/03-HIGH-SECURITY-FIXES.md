## Database findings (migration 157)

| ID | Original issue | Fix | Tests (`tests/remediation/40-db-high.test.ts`) | Residual risk |
|---|---|---|---|---|
| **D-004** | A permissive storage policy let any signed-in user list files in, and upload into, any request's attachment folder (upload reproduced in the audit) | The two permissive policies are dropped. The app already uploads, downloads and removes through its server client, so nothing legitimate depended on them | An unrelated requester cannot upload into another request's folder (the original attack), cannot download or list its files; **positive:** the server can still upload, download and remove | None known |
| **D-006** | Company-wide settings tables (business hours, holidays, escalation rules, task and request priorities, app settings…) had no organization column, were readable without signing in, and any organization's manager or admin could change them (3 live repros) | Anonymous rights revoked; write rights removed from client roles (all writes already go through the server client) | Not readable without signing in; cannot be changed by a manager or an admin (the original attacks); **positive:** signed-in users still read them, the server can still change them | They remain shared across organizations by design (no org column) — a multi-tenant design point for later |
| **D-008** | A requester could insert a ticket that was already closed with a far-future due date, and a technician could renumber a ticket or change when it was created | A trigger refuses, for client roles: a new ticket that is not an ordinary open/pending-approval, unassigned one with no SLA clock or lifecycle stamps, and any change to a ticket's number or creation time | Both original attacks refused; **positive:** a requester can still create an ordinary ticket and a technician can still change their team's tickets | See regression R-2 in document 05: the web ticket-creation code set SLA deadlines in the user's insert; it now sets them with the server's client right after, so the database rule stays intact |
| **D-010 (database part)** | Deactivating a user did not revoke access in the database | `current_org_id()` and `current_user_role()` now require `is_active`, so a deactivated user sees nothing even with a session still open | Own tickets and other people's disappear as soon as the account is inactive | None |
| **D-014** | The task-delete rule had no organization predicate (only PostgREST's "DELETE needs WHERE" protected it); partly tested in the audit | Organization predicate added | A manager cannot delete another organization's task and still can delete one of their own | The finding was **not separately exploitable through the API** in the audit, so the fix is defensive |
| **D-015** | Internal notes were visible to "any team member", not to the ticket's own team | The rule now checks the ticket's team | A technician who raised a ticket to another team cannot read that team's internal notes (the original gap); **positive:** a plain requester never sees internal notes but sees public replies | None |
| **D-054** | An attachment row's `storage_path` could be pointed at another request's file, or its type rewritten, through the API | A trigger: on insert the file must be in the request's own folder; on update only the deleted flag can change | Only the deleted flag can be changed; the file must be in the request's own folder | None |

## Application findings

| **D-017** | Sign-in and forgot-password limits were keyed on the client-supplied `X-Forwarded-For`: unlimited guesses by rotating it, or a shared bucket that locked others out | `lib/rate-limit.ts`, `lib/actions/auth.ts`, `lib/actions/approvalEmail.ts` | Sign-in is limited **per account**; forgot-password is limited **per address being mailed** (3 per hour); a per-caller-address limit is applied only when the address is trustworthy (`TRUSTED_PROXY_HOPS`) and then uses the entry the nearest trusted proxy appended | `tests/unit/rate-limit-client-ip.test.ts` (7 tests): forwarding headers are ignored with no trusted proxy; one trusted proxy uses the right entry; two proxies take the second from the right; a short header is not believed; rotating the header does not buy more guesses; one account being tried does not lock out another; four requests for one address from four callers send three e-mails | **Deployment decision:** with `TRUSTED_PROXY_HOPS` unset (0) the per-address limit is off and only the per-account limits apply. ## Not changed — and why

| ID | Finding | Status | Reason and recommended next step |
|---|---|---|---|
| **D-005** | No confidentiality tier for HR / Finance-style teams: any manager+ sees every team's requests | **Requires user approval** | It is a design decision about who may see what (a "restricted team" flag, how managers are excluded, how reporting treats them). It is a significant change to the permission model, which this remediation was told not to make without approval. Recommended: decide the policy, then implement as a team-level `restricted` flag enforced in the ticket row-security rule |
| **D-011** | Bulk-import default password `Welcome@123` is hard-coded and the forced reset is enforced only by the screen | **Requires user approval** | Changing it changes how every bulk-imported user signs in for the first time (one-time invite links versus a shared default). Recommended: generate a random one-time password or send invite links, and enforce `must_reset_password` in the sign-in action |
| **D-018** | The deployment appears to run over plain HTTP; cookies lack `Secure` | **Deferred (production decision)** | The public URL today is `http://182.72.84.10:3210`; marking cookies `Secure` and enabling HSTS only works once the site is served over HTTPS (a certificate and proxy decision). Setting them now would stop everyone from signing in. Recommended: put TLS in front of the app first, then set the cookie flag and HSTS (the response headers added under D-033 deliberately leave HSTS out for this reason) |
