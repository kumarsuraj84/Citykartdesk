# CityKart Desk — Full Codebase Audit (2026-08-08)

**Status: READ-ONLY FINDINGS. No code has been changed as a result of this audit.**
Per the audit brief, all fixes require explicit approval before implementation.

**Methodology:** Six independent read-only audit passes (Database/RLS/Security, Server
Actions, Queries & Calculations, API Routes, Frontend State/UX, Imports/Dead-code/Config),
each instructed to be exhaustive within its scope and to cite only file:line evidence
actually read. The Frontend State track further split into four domain sub-audits (Tasks,
Requests/Projects, Admin/Approvals, Shared/Layout/Intake) given the size of the client
surface. All ~90 findings below are drawn directly from those reports.

---

## 1. Executive Summary

The codebase is in good shape mechanically — TypeScript and ESLint are both clean — but
this audit surfaced a **consistent, repeated authorization gap**: across projects, tasks,
admin config, exports, and intake, mutating server actions check "is the caller logged
in?" but not "is the caller allowed to touch *this* row?" This pattern recurs in well over
a dozen files. The two Critical database findings are historical (already fixed by a later
migration), but the equivalent gap is still live today at the application layer (Server
Actions §H-1/H-5/H-6/H-7, this doc §3).

Beyond authorization, three more themes repeat across every track:
- **Optimistic UI with no rollback on error** — dozens of components across Tasks,
  Requests, Projects, and Admin update the screen before the server confirms, and never
  revert or show an error if the server rejects the change. Users see values that were
  never actually saved.
- **N+1 / unbounded queries** — the exact pattern already fixed once for project-list
  progress recurs one level down (milestones) and in the audit log, analytics dashboards,
  and services catalog.
- **Duplicated constants** — priority style maps (colors/labels) are independently
  reimplemented in 8+ files with three different color palettes for the same four values.

Three **real data-loss/correctness bugs** were also found that need prompt attention
regardless of security scope: editing a Knowledge Base article wipes its content,
approval workflow steps never load after a page reload, and a project's cancelled-status
count doesn't reconcile with its own "Total" KPI card.

## 2. Critical Findings

### C-1 — Historical: dangling `DROP POLICY` defeated org isolation on ~13 tables
**Severity:** Critical (fixed) · **Category:** Dangling Policy / Cross-tenant Leak
**File:** `supabase/migrations/20240101000033_org_isolation.sql` (root cause) → fixed by
`20240101000080_rls_hardening_cross_tenant.sql`
**Description:** Migration 033's `DROP POLICY IF EXISTS "<invented-name>"` statements
never matched the real pre-existing policy names, so the old (weaker) policies stayed
live and Postgres OR-combined them with the new org-scoped ones — the new policy never
actually restricted anything. Confirmed on `profiles`, `services`, `service_categories`,
`departments`, `approval_workflows`, `approval_workflow_steps`, `global_sla_config`,
`task_templates`/`task_template_items`, `team_members` (worst: allowed cross-org
INSERT/UPDATE/DELETE of team membership), `teams`, and both `request-attachments` storage
policies (INSERT and SELECT).
**Root cause:** Policy names were guessed instead of checked against `pg_policies`.
**Impact (historical):** Any authenticated user — and for `global_sla_config`/
`task_templates`, any *unauthenticated* anon-key request — could read/write other orgs'
data for the window between migration 033 and 080.
**Current status:** Fixed in `20240101000080`. **Residual debt:** the table-level
`GRANT ALL ... TO anon` on `global_sla_config`/`task_templates`/`task_template_items` is
never revoked in any of the 85 migrations — RLS now blocks it in practice, but the grant
itself should still be revoked as defense-in-depth.
**Recommended fix:** `REVOKE ALL ON TABLE global_sla_config, task_templates,
task_template_items FROM anon;` in a follow-up migration. Add a CI check that fails a
migration if `DROP POLICY IF EXISTS "X" ON t` has no matching prior `CREATE POLICY "X" ON
t` anywhere in history — this bug recurred 13 times.

### C-2 — Historical: `requests_select` lost its org guard for 3 migrations
**Severity:** Critical (fixed) · **Category:** Cross-tenant Leak
**File:** `supabase/migrations/20240101000042_fix_collaborator_rls_recursion.sql:14-19` →
fixed by `20240101000045_rls_optimization.sql:8-11` (which documents the regression in its
own header comment)
**Description:** A recursion bug-fix rewrote `requests_select` and dropped the
`org_id = current_org_id()` clause entirely, leaving `requester_id = auth.uid() OR
is_team_member(team_id) OR current_user_role() IN ('manager','admin')` — any manager/admin
in any org could read every org's requests.
**Current status:** Fixed. **Recommended fix:** add an automated RLS regression test
suite (e.g. pgTAP) asserting org isolation after every migration.

### C-3 — Task custom-field actions have zero authorization
**Severity:** Critical · **Category:** Missing Auth Check · **File:** `lib/actions/tasks.ts`
**Function:** `createCustomField` (630), `updateCustomField` (665), `deleteCustomField`
(683), `setCustomFieldValue` (694)
**Description:** All four use `createAdminClient()` (bypasses RLS) but check only
`if (!profile) return`. No role check at all.
**Impact:** Any signed-in user, including a requester with no team, can create/update/
delete custom field *schema* for any team, or set arbitrary values on any task.
**Repro:** As a "requester", call `createCustomField({ teamId: <any>, name: 'x',
fieldType: 'text' })` — succeeds.
**Recommended fix:** Add a role check (`agent`/`manager`/`admin`/`platform_owner`),
matching `lib/actions/admin/config.ts`'s bar for equivalent schema-management actions.

### C-4 — Editing a Knowledge Base article wipes its content
**Severity:** Critical · **Category:** Data Loss · **File:**
`app/(app)/admin/knowledge-base/KnowledgeBaseClient.tsx:45-49,59-66`, root cause shared
with `lib/actions/knowledge-base.ts:59-64`
**Description:** The `Article` type used by the list never includes `content` (bandwidth).
`openEdit(a)` seeds the edit form with `content: ''`. `handleSave` calls
`updateKbArticle(id, title, content, status)`, which unconditionally overwrites the stored
content column with whatever's in the form.
**Impact:** Clicking Edit on any article, then Save — even without touching the content
box — silently deletes the article body.
**Repro:** Create an article with content, go back to the list, Edit, Save without typing
anything.
**Recommended fix:** Fetch full article content (including `content`) when opening edit,
or omit `content` from the update payload when the local field was never populated.

### C-5 — Approval workflow steps never load after page reload
**Severity:** Critical · **Category:** Missing Data Fetch · **File:**
`app/(app)/admin/approvals/WorkflowBuilderClient.tsx:520-522`
**Description:** The client seeds `steps: []` unconditionally for every workflow.
`getApprovalWorkflows()` (used by the page) never fetches steps; a batched
`getApprovalWorkflowWithSteps()` exists in `lib/queries/admin.ts` but is never called from
this client.
**Impact:** Expanding any workflow that already has steps (its own badge correctly shows
e.g. "3 steps") renders "No steps yet." Admins cannot see/edit existing approval chains
after a reload — only steps added in the current session are visible.
**Recommended fix:** Fetch steps on card expand, or have the page load full
workflow+steps up front.

### C-6 — Routing rule list goes stale after create/edit
**Severity:** Critical · **Category:** Broken Prop-Sync · **File:**
`app/(app)/admin/routing/RoutingRulesClient.tsx:664-675,386-416`
**Description:** `useState(() => { setRules(initialRules) })` — a function passed to
`useState` runs once at mount only, not on every prop change, despite the comment "Keep
rules in sync with server data after revalidation." `RuleModal.submit()` never patches the
parent's `rules` array either.
**Impact:** After creating/editing a routing rule, the on-screen list does not change —
admin has no confirmation the save worked, may resubmit, until a manual hard reload.
**Recommended fix:** Use the render-time-comparison pattern already established in
`ProjectsTable.tsx:66-80`, or have `onClose` pass the saved rule back so the parent can
splice it in directly.

### C-7 — Audit Log page loads the entire activity history into memory
**Severity:** Critical · **Category:** Missing Pagination · **File:** `lib/queries/admin.ts`
**Function:** `getAuditLogs`, lines 224-289
**Description:** No `.range()`/`.limit()` on the `request_activity`/`task_activity`
selects — both full result sets are pulled into Node, merged, sorted in JS, and only then
sliced for the requested page.
**Impact:** Every view of `/admin/audit` fetches every activity row the org has ever
generated, unbounded. Scales to OOM/timeout as the org's history grows.
**Recommended fix:** Push `.range()` per table before merging, or do the merge/sort in SQL
(a small view or RPC), since two independently-paginated tables can't be correctly
interleaved by slicing each at the same page boundary.

## 3. High Severity Findings

### Database / RLS / Security
- **H-1 — Broad, currently-live `createAdminClient()` calls with no `org_id` scoping**
  across `lib/actions/admin/org.ts` (departments/locations/cost-centers/user org fields),
  `admin/config.ts` (app settings, task templates, business hours, holidays, escalation
  rules, alert rules, tags, request priorities, retention policy — `updateSLATier` in the
  *same file* was already fixed with this exact pattern, never propagated to siblings),
  `admin/teams.ts`, `admin/workflows.ts`, `admin/routing.ts`, `admin/reports.ts`
  (`getScheduledReports` returns **every org's** scheduled reports including recipient
  email lists to any admin/manager, no filter at all), `admin/services.ts`,
  `admin/task-config.ts`, `intake/flags.ts`, and `tasks.ts`'s custom-field functions (see
  C-3). **This is today's real attack surface** — RLS gaps get fixed, admin-client
  bypasses get none of RLS's protection. **Fix:** a typed `orgScopedAdminUpdate(table, id,
  orgId, patch)` wrapper requiring an explicit `orgId`, migrated in everywhere above.
- **H-2 — `proxy.ts`'s route matcher has no `/api/**` exclusion**, so cron/webhook
  requests (no session cookie) get redirected to `/login` before the route's own
  `x-cron-secret` check ever runs — the 3 registered Vercel cron jobs and the Microsoft
  Graph webhook-validation handshake cannot function as written. **Fix:** narrow-exclude
  only the specific cron/webhook/health paths, not a broad `/api/*` (which would strip
  session gating from every other API route).
- **H-3 — Cron routes check the wrong header** — `alerts/run`/`escalation/run`/
  `desktime/sync` only check legacy `x-cron-secret`; Vercel Cron sends `Authorization:
  Bearer <secret>`. Even after H-2, these routes would still 401 real cron invocations.
  `intake/cron/classify` already checks both — mirror that.
- **H-4 — `alerts/run`'s notification pipeline has no org scoping** on `alert_rules` or
  the recipient-selection query (`getProfilesByRoles`) — dormant under single-org
  deployment, but the moment a second org exists, users would receive other orgs' task
  titles/due dates/links in notifications and email.
- **H-5 — `lib/actions/projects.ts` mutations have no ownership/membership check** beyond
  "is logged in": `updateProject`, `archiveProject`, `attachToProject`, `createMilestone`/
  `updateMilestone`/`deleteMilestone`, `assignTaskMilestone`, `addProjectMember`/
  `removeProjectMember`, `createProjectUpdate`/`deleteProjectUpdate`. Any authenticated
  user can archive/reassign any project, add themselves as owner of any project, or delete
  another author's status update.
- **H-6 — `exportTasks`/`exportProjects` skip the role bar their siblings enforce** —
  `exportRequests`/`exportApprovals` require admin/manager/platform_owner;
  `exportTasks`/`exportProjects` only check authentication, letting any user bulk-export
  the whole org's task/project data (up to 10,000 rows).
- **H-7 — `sendFromMessage` can send outbound org email with no ownership/role check** —
  any authenticated user can trigger a reply/reply-all/forward against an arbitrary
  `messageId` with attacker-chosen `toAddresses`/subject/body — a phishing/spam vector
  using the company's own domain.
- Also High: `deleteNote` (intake) has zero authorization at all; `markMessageRead`/
  `archiveMessage` have no auth check and can't detect an RLS no-op as a real failure
  (looks like success either way); `getReclassifyProgress` has no auth check and no org
  filter (cross-org intake-volume disclosure).

### Server Actions
- **Missing Auth/Ownership across `lib/actions/tasks.ts`** — `updateTaskStatus`,
  `updateTaskField`, `updateTaskSource`, `updateTaskTags`, `updateTaskDates`,
  `addTaskAssignee`/`removeTaskAssignee`, `toggleSubtaskDone`, `removeTaskDependency` all
  check only `if (!profile)`. Contrast with `deleteTask` in the same file, which correctly
  checks `created_by`/role. Any signed-in user can mark another team's tasks done/
  cancelled, reassign them, or strip dependency links.
- **`submitForApproval`'s "already in progress" check doesn't filter by status** — a real
  TOCTOU race. Migration 031 deliberately dropped `UNIQUE(approvals.request_id)` "to allow
  multiple sequential approval rounds," but the existence check in `submitForApproval`
  (unlike its correct sibling `sendAdHocApproval`, which adds `.eq('status','pending')`)
  still queries *any* approval row — permanently blocking re-submission after one round
  completes, **and** allowing two concurrent calls to both pass the check and create two
  simultaneous pending approvals (nothing in the DB prevents it). **Fix:** add
  `.eq('status','pending')` to the check, and add a partial unique index
  `UNIQUE(request_id) WHERE status='pending'`.
- **Round-robin routing index has no optimistic-concurrency guard** (`lib/routing/
  assign.ts:45-54`) — concurrent request creation can read the same `last_assigned_index`
  twice, assigning the same person twice while only advancing the counter once, silently
  skewing fairness.

### Queries & Calculations
- **`getMilestoneProgress` called in a loop** on the project detail page — the exact N+1
  pattern already fixed once for `getProjectsProgress`, recurring one level down. No
  `getMilestonesProgress(milestoneIds)` batched sibling exists.
- **Services catalog homepage over-fetches** — `getCategoriesWithSubCategories`/
  `getCategoryBySlug` use the full `SERVICE_SELECT` (incl. `form_fields`/`sla_config`
  JSONB + 7 full-row joins) even though a purpose-built lean `SERVICE_CARD_SELECT` already
  exists and is correctly used elsewhere.
- **Analytics dashboards pull entire tables and aggregate in JS** — `getAnalytics`,
  `getTaskAnalytics`, `getProjectAnalytics`, `getWorkloadReport` all fetch unbounded
  row sets and do all counting/grouping in JavaScript instead of SQL `GROUP BY`/`FILTER`,
  unlike the correctly-aggregated `get_home_dashboard` RPC.

### API Routes
- **Three alert types (`task_due_soon`/`task_overdue`/`daily_digest`) are DB-insert
  no-ops** — cast to a `NotificationType` value that was never added to the Postgres
  enum. Every insert fails; `notify()` only `console.error`s. The route still reports
  non-zero success counts, so it looks healthy while in-app notifications for these three
  alert types silently never appear.
- **DeskTime sync and intake auto-classification cron jobs are orphaned** after the
  Vercel→Railway migration — `vercel.json` still lists all three original cron paths, but
  the actual Railway scheduler (`scripts/cron-tick.mjs`, default `CRON_JOBS=
  "escalation,alerts"`) can't address either job's URL shape even if added, and
  `intake/cron/classify` expects Vercel's `Authorization: Bearer` convention, not
  Railway's `x-cron-secret`.

### Frontend State — systemic across all 4 domains
- **Optimistic updates with no error check/rollback** recur in: `RequestSidebarPanel`
  (status/priority/assignee), `TaskDetailPanel` and `TaskDetailInline` (status/priority/
  assignee/due-date/project/tags), `CustomFieldCell`, `SubtaskList.handleToggle`
  (inconsistent with its own sibling `handleDelete`, which does this correctly),
  `TaskInlineTitle`, every inline cell editor in `TaskTable.tsx` (status/priority/due-date/
  assignee/milestone/title), and — notably — `ProjectHeader.patch()`,
  `ProjectCard.patch()`, `ProjectMembers`, and `ProjectsTable.patch()` (all four discard
  the server action's error, in the *same file* as `ProjectHeader.changeStatus()`, which
  is the codebase's own reference-correct pattern sitting right next to the bug),
  `MilestoneTable`'s `ProgressCell`/`patch()`, `WorkflowBuilderClient.handleMoveStep`,
  `TaskConfigClient`'s two reorder handlers, `NotificationBell`/`NotificationsClient`
  (mark-read/archive/mark-all), `WorkspaceClient.handleToggleRead`, `ReviewClient`'s
  mark-read/archive. In every case: a failed server-side update leaves the UI showing the
  new (unsaved) value indefinitely with no error message, until an unrelated refresh
  silently reverts it.
- **Keyboard/screen-reader inaccessible controls**: `InboxList` message rows (only the
  star button is focusable — the primary "open message" action is not), `SourceCell`'s
  `role="button"` trigger (no `onKeyDown`, so Enter/Space do nothing despite the ARIA
  role claiming otherwise). Both High because they block the primary interaction, not a
  secondary one.
- **Race condition in the intake reading pane** — rapid message switching has no
  request-id guard, so a slower first fetch can resolve after a faster second one and
  silently show the wrong message's content while the list still highlights the correct
  one.

### Imports / Dead code / Config
- **`README.md` is unedited `create-next-app` boilerplate** — points at a non-existent
  `app/page.tsx` and recommends Vercel deployment, directly contradicting
  `docs/RAILWAY-DEPLOYMENT.md`.
- **`DATABASE.md`/`ARCHITECTURE.md` both claim "66 migrations"; actual count is 85** — the
  entire Projects/Milestones, DeskTime, and Job-Functions/Designations schema (38
  migrations, ~45% of the total) is completely undocumented in the schema reference.
- **No `.env.example` anywhere** — ~33 distinct env vars are referenced across the app and
  the separate `api/` worker service; only ~9 are documented anywhere. High risk of a
  broken deploy from a missing OAuth/LLM/intake secret with no reference to catch it.

## 4. Medium Severity Findings (grouped, condensed)

- **Two index "upgrades" are silent no-ops** — migrations 043/028 tried to replace an
  earlier index (add a `WHERE` clause; add a composite sort column) by reusing the same
  index name with `CREATE INDEX IF NOT EXISTS`. Postgres only checks the name, so the
  intended optimization never applied in any real environment (`idx_tasks_parent`,
  `idx_task_activity_task`).
- **`getProjectStats()`'s "Total" doesn't reconcile with its own status buckets** —
  cancelled projects count toward `total` but aren't bucketed into any of the four
  displayed cards, so the KPI numbers visibly don't add up.
- **PostgREST `.or()` filter injection from unescaped search input** in `lib/actions/
  search.ts`, `lib/queries/services.ts`, `lib/actions/requests.ts` — a comma/paren in a
  search string can inject extra filter clauses (bounded blast radius: still inside RLS,
  can't escape the caller's authorized scope, but genuinely unsanitized). The codebase
  already has the right fix pattern (`sanitizeQuery()` in `requests.ts`) — just not
  applied everywhere.
- **`is_team_member()` SECURITY DEFINER lost its `search_path` pinning** when
  `CREATE OR REPLACE`d by migration 036 — a known Postgres privilege-escalation vector
  class; `is_request_collaborator()` and `get_enabled_modules()` share the same gap.
- **HTML/email injection via unescaped titles** in notification emails — task/milestone/
  project titles are interpolated into email HTML with zero escaping, and a task title can
  originate from an external, unauthenticated email `Subject:` header via the intake
  pipeline.
- **`/api/admin/audit` has no upper bound on `perPage`** and fetches full result sets
  before paginating (same root cause as C-7, different route).
- **`/api/health` is unauthenticated, hits the DB on every call**, and leaks raw error
  text to any caller — cheap DoS amplification vector.
- **Duplicated priority style/label maps across 8+ files**, three different color
  palettes for the same four values (request priority), plus a separate duplication for
  task priority (6 files) and a verbatim-copied `PRIORITY_ORDER` array (5 files, project
  priority) — see §7.
- **8 fully-built components are never imported anywhere**, including `ErrorBoundary`
  (meaning no route/layout is actually catching unhandled render errors in production) and
  `TaskDetailSidebar` (superseded by `TaskDetailPanel`/`TaskDetailInline` but left in
  place).
- **`deleteAttachment` is fully implemented server-side with no UI to call it** — users
  can upload attachments but never delete one.
- **URL-state inconsistency** — several filter/tab UIs keep state in local `useState`
  instead of the URL, unlike sibling features that correctly do this: `TaskTable`'s
  in-table status tabs, `RequestDetailTabs`/`ProjectDetailTabs`'s active tab,
  `UserManagementClient`'s search box, `AuditLogClient`'s four filters, `InboxList`'s
  search/sort/stage filter (folder/channel *are* URL-synced in the same component — the
  other three aren't).
- **`orphaned vercel.json`** still declares Vercel cron jobs after the Railway migration,
  with schedules that don't even match the documented Railway replacement.
- **`next.config.ts` disables build-time type checking** (`ignoreBuildErrors: true`) —
  currently harmless (tsc is clean) but a foot-gun if `types/database.ts` regeneration is
  ever skipped, with CI enforcement as the only backstop (not verified in this pass).

## 5. Low Severity / Cleanup

- Timing-unsafe (`!==`) secret comparisons on 6 cron/webhook routes, vs. the correct
  `crypto.timingSafeEqual` pattern already used in `lib/intake/oauth.ts`.
- `get_home_dashboard()` trusts caller-supplied `p_is_manager`/`p_is_agent` booleans
  instead of re-deriving from `profiles.role` — low impact, bounded by existing RLS on the
  underlying rows.
- Chart components (`Charts.tsx`) key `.map()` output on array index — low risk given
  they're non-reorderable, but worth fixing for correctness hygiene.
- Sidebar collapse toggles and the notification-bell popover are missing `aria-expanded`/
  `aria-haspopup`.
- `GlobalSearch`'s debounced fetch has no `catch` (silent stale-results-on-failure) and no
  request-ordering guard.
- Leftover "Cognix" branding in 20 files (worker package name, theme localStorage key, a
  manual SQL script filename, several docs) after the CityKart rebrand.
- `tailwindcss-animate` is an unused devDependency (superseded by `tw-animate-css`);
  `shadcn` CLI is listed under `dependencies` instead of `devDependencies`.
- Several small dead exports (query functions with zero callers, unused type exports) —
  see full sub-report for the complete list; low individual risk, worth a batch cleanup.

## 6. Cross-Cutting Patterns (read this section first when prioritizing)

1. **"Logged in" is being used as a proxy for "authorized."** This is the single most
   repeated defect class across both the Database/RLS and Server Actions tracks. It
   affects Projects, Tasks, custom fields, exports, admin config (departments/locations/
   cost-centers/teams/workflows/routing/scheduled-reports), and one intake action that can
   send outbound email. A shared authorization helper (role + org/ownership check) applied
   consistently would close most of §3's Server Actions findings and §2/§3's Database
   findings in one pass, rather than 20+ individual patches.
2. **Optimistic UI without rollback** is the single most repeated defect class in the
   Frontend State track — it appears in Tasks, Requests, Projects, and Admin, including
   right next to the codebase's own correct reference implementation
   (`ProjectHeader.changeStatus`) in three cases. A shared `useOptimisticAction` hook
   (capture-prev / apply / revert-on-error) would eliminate the whole class at once.
3. **N+1-by-loop recurs even after being fixed once** — the milestone-progress instance is
   structurally identical to the already-fixed project-progress bug, just one level
   further down the same file. Worth grepping for `.map(async` / `for (... await` across
   `lib/queries` and `lib/actions` as a dedicated sweep rather than trusting it won't
   recur a third time.
4. **A fix applied to one function is rarely propagated to its siblings** — this shows up
   repeatedly: `updateSLATier`'s org-scoping fix never reached 6+ sibling functions in the
   same file; `deleteTask`'s ownership check never reached 8+ sibling task mutations;
   `sendAdHocApproval`'s `status='pending'` filter never reached `submitForApproval`;
   `handleDelete`'s rollback pattern never reached `handleToggle` in the same
   `SubtaskList.tsx` file. When fixing any one of these, grep the same file/directory for
   the same shape before considering it done.

## 7. Duplicated Priority-Style Maps (consolidation opportunity)

Confirmed independently by both the Frontend State and Imports/Dead-code tracks. At least
8 files hand-roll a `{low,medium,high,urgent} → Tailwind classes` map for request
priority alone, with three visibly different color palettes for the same four values
(`RequestTasksTab.tsx`, `SLAConfigClient.tsx`, `TaskTemplatesClient.tsx`, `Charts.tsx`,
`DetailDrawer.tsx`, `RequestBadges.tsx`'s own label/arrow maps, `InboxList.tsx` and
`ReviewClient.tsx`'s two independently-named `PRIORITY_PILL`s) despite a canonical
`lib/constants/requests.ts` already existing and being under-used. Task priority repeats
the same pattern across 6 more files. Project priority order (`['P1','P2','P3']`) is
copy-pasted verbatim in 5 files even though `ProjectPriorityBadge.tsx` already centralizes
the *style* map — the *order* constant just never got added alongside it. (Note: this
session's own work added the `chip-3d` visual treatment to most of these maps in place —
it did not consolidate the underlying duplication, which remains open.)

## 8. What Was Verified As Correct (do not re-review)

- No plaintext secrets anywhere; service-role key is server-only and never imported from
  a client component; IMAP/DeskTime credentials are stored only as Supabase Vault
  references with decrypt RPCs locked to `service_role`.
- `lib/actions/admin/users.ts` (`setUserTeams`/`adminSetPassword`) — the strongest
  IDOR-prevention pattern found in the codebase; explicitly re-verifies target org match.
- `lib/actions/intake/channels.ts`, `intake/reviews.ts`, `intake/rules.ts`, `intake/
  work.ts`'s core paths, `admin/desktime.ts`, `admin/integrations.ts` — consistent role
  checks and org scoping throughout.
- `TaskBoardView.onDragEnd`, `RequestBoardView.onDragEnd`, `ProjectHeader.changeStatus`,
  `TaskActivityFeed`'s optimistic comment posting, `SubtaskList.handleDelete`,
  `ProjectCell.tsx` — all correctly implement optimistic-update-with-rollback; these are
  the reference patterns the rest of the codebase should be brought in line with.
  `getProjectsProgress`, `get_home_dashboard` RPC, attachment signed-URL batching,
  approval steps/decisions batching, routing-rule name-lookup batching — all confirmed
  already-optimized, no N+1.
- OAuth `state` handling (HMAC-signed, constant-time-verified, 15-minute expiry),
  `intake/oauth/callback` and `/start` (session re-derivation, org-scoped channel
