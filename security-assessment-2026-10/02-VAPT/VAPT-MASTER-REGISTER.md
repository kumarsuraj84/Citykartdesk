## 1. How to read this

This is the single list of security weaknesses found in Citykart Desk by the internal vulnerability assessment and penetration test of 2026-10-15. It has one row for each distinct weakness. A weakness that showed up in several places, or that two or more reviewers reported under different numbers, is shown once, and every original number is kept in the "Also reported as" column. The row numbers are `VAPT-001` and so on; the two dependency findings are `VAPT-DEP-01` and `VAPT-DEP-02`.

Four things to know before using any number in this file:

1. **Nothing here is deployed.** Every "Fixed" means fixed in the LOCAL working copy (branch `security/vapt-iso27001-soc2-local`) and proven only on the isolated test stack. Production runs build `20261015-145217` (main `717e5c6`), which does NOT contain any of these fixes. The database change `supabase/migrations/20240101000164_vapt_security_hardening.sql` has not been applied to production.
2. **Status words are copied from the lead tester's status table** (`05-REMEDIATION/00-FINDING-STATUS-TABLE.md`) and never upgraded. Where a row combines a fixed part and an open part, it is "Partially Fixed". A few rows use a status that is derived rather than copied from a single line of the table; they are listed in section 3.3.
3. **Severity is the assessor's rating, not a CVSS score.** The only number shown is the publisher's figure for the framework advisory (VAPT-DEP-01), and it is marked as copied. Where a reviewer gave a range (for example "Low to Medium"), the higher label is used, so the counts lean toward over-stating risk rather than hiding it. "Low (informational)" is counted as Low. npm's "moderate" is read as Medium.
4. **"Fixed" does not mean equally well proven.** Section 2.2 splits the fixed rows by how they were proven. Fixes proven only by reading the code are marked CODE in the Test column.

Evidence classes used (from the assessment brief): **A** = verified LOCAL technical evidence (our own tests on the isolated stack); **B** = repository evidence (source, migrations, policy text); **C** = authorised organisational evidence (none has been supplied, so none is claimed); **D** = documentation only; **E** = missing or not verified. This register uses A and B only.

Test abbreviations: T10 = `tests/vapt/10-confidentiality-exploits.test.ts`; T11 = `tests/vapt/11-integrity-exploits.test.ts`; T12 = `tests/vapt/12-email-reply-participant.test.ts`; TU = `tests/unit/vapt-hardening-units.test.ts`; TB = `tests/unit/approval-code-burst.test.ts`; H = an HTTP probe against the rebuilt isolated app, captured in `02-VAPT/HTTP-PROBE-CAPTURES.md` and described in `02-VAPT/03-MANUAL-PENETRATION-TESTING.md`; M164 = migration `20240101000164_vapt_security_hardening.sql`.

## 3. Resolved conflicts, derived statuses and limits (read before relying on the counts)

### 3.1 Resolved: approval-code test failures

An earlier recorded run (16:14 to 16:17) showed four failing approval-code tests (three D-060 cases in `110-approval-hardening`, one in `approval-email-link`). The lead tester found the cause: the tests' helper still looked for the code in the e-mail subject after the code moved to the body, and the helper pattern was fixed. It was **not** a product defect. E-mail approval works: `approval-email-link` passes 11 of 11, and the final remediation and default suites are green (section 2.3). VAPT-033 and VAPT-043 are therefore shown without any re-run flag.

### 3.2 Supporting files now present

The manual penetration log is `02-VAPT/03-MANUAL-PENETRATION-TESTING.md` (the status table still calls it `04-MANUAL-PENETRATION-TESTING.md`; its own naming note says they are the same file), and the raw probe output is in `02-VAPT/HTTP-PROBE-CAPTURES.md`. Both were written after the first version of this register. The H results (VAPT-028, 029, 038, 067, and the header check in VAPT-002 and VAPT-DEP-01) are cited from the captures.

### 3.4 Other limits

- Findings marked B were reviewed in code and policy text but not exploited. Several were marked PLAUSIBLE by the reviewers and need a dynamic check.
- The audit database holds one organisation, so every cross-organisation point (VAPT-021, 048) rests on policy text.
- Production settings (sign-up, token lifetime, TRUSTED_PROXY_HOPS, separate secrets, whether the intake worker runs) are not visible from the repository and were not read. Rows that depend on them say so.
- The green regression result proves the LOCAL code only. Production runs build 20261015-145217 with Next.js 16.2.9 and none of the fixes.

## 5. The ten findings that matter most, in plain language

How these ten were chosen: highest severity first; at equal severity, findings that are still open (or need a decision) come before fixed ones; and the widest exposure comes first (anything an outsider can reach before anything only an insider can). The first four are Critical or High. The last six are Medium: VAPT-023 (not verified, but potentially wide), VAPT-032 (it makes VAPT-003 easier to abuse), VAPT-006 and VAPT-007 (open or partly open, and they affect the integrity of service-level reporting), and VAPT-012 and VAPT-011 (the two staff-only-information leaks proven with a before/after exploit test). Everything else is in the register in section 4.

### 1. VAPT-DEP-01 — Web framework Next.js 16.2.9 has 16 published security advisories, including remote code execution on Windows hosts

- **Problem:** The website is built on a framework called Next.js. The version in use (16.2.9) has 16 published security notices. The worst one (GHSA-p293-qw3h-jr36, rated 9.0 out of 10 by its publisher) lets an outsider run commands on a Windows server without signing in. It is fixed from version 16.3.3. A second one, in the image optimiser, was judged not reachable here.
- **Business risk:** Whoever used it would control the machine that runs the application and holds its database login: every ticket, every account and every attachment. Production is a Windows server reachable from the internet through a port forward (http://182.72.84.10:3210), so the exposure is real and continues until the new version is released.
- **Where found:** The framework dependency in `package.json` and `package-lock.json`.
- **How we checked:** We ran `npm audit --omit=dev` on the working copy, before and after the change. We checked the image-optimiser notice with HTTP probes (H1): the AVIF format is not produced and remote or loopback image addresses are refused. The final local checks pass: type check 0 errors, default suite 234 files and 1760 tests, production build.
- **What we changed:** Raised `next` and `eslint-config-next` from 16.2.9 to 16.3.8 and ran `npm audit fix`.
- **What happened after the fix:** Production-dependency findings fell from 9 (1 critical, 5 high, 3 moderate) to 2 moderate (VAPT-DEP-02); the critical count went from 1 to 0. The Windows file-system advisory does not depend on the image route and still applies to production until it is upgraded.
- **What remains:** Nothing is deployed: production still runs 16.2.9. Management must decide when to release, and the new version should first go through a user acceptance test (for example the 20 MB upload in VAPT-035). No automatic dependency check exists, so new notices will appear again.
- **Status:** Fixed (Critical) - fixed in the LOCAL working copy only, not deployed
- **Technical evidence:** Class A (local scan output and probe H1 in `02-VAPT/HTTP-PROBE-CAPTURES.md`). Advisory GHSA-p293-qw3h-jr36, fixed in 16.3.3. Publisher figure 9.0 copied from the status table; CVSS version not re-checked.

### 2. VAPT-002 — Sign-in and session traffic runs over plain HTTP; login cookies are not marked Secure and can be read by scripts; no HSTS; CSP only reports

- **Problem:** People reach Citykart Desk over plain, unencrypted HTTP. The login cookie is not marked Secure, can be read by page scripts and lasts about 400 days. There is no instruction forcing browsers to use HTTPS (HSTS), and the content-security policy only reports problems instead of blocking them.
- **Business risk:** A password or a login cookie can be read by anyone on the network path: shop Wi-Fi, a provider, a compromised router. A copied cookie lets the thief act as that person, including as an administrator. This is the most likely way for an outsider to get into the system today.
- **Where found:** `proxy.ts` lines 103-111 and `lib/supabase/server.ts` lines 18-24 (cookie options passed through), `next.config.ts` lines 72-87 (no HSTS; report-only policy), `lib/http/csp.ts` line 14. The public address is http://182.72.84.10:3210.
- **How we checked:** Source review, then a browser check on the final build signed in as a synthetic technician (probe H6): the login cookie was readable by page scripts and not Secure over http; no HSTS header is sent over http.
- **What we changed:** The code is now HTTPS-ready: session cookies are marked Secure and HSTS is sent as soon as the site address starts with https. Nothing changes over plain http. HTTPS itself needs a decision: put a reverse proxy with a certificate in front of the app.
- **What happened after the fix:** Over http nothing changes, by design. The https behaviour is code only and cannot be tested until HTTPS exists.
- **What remains:** The finding stays Requires Decision because HTTPS is not in place, so users are exposed exactly as before. Once HTTPS exists: confirm the Secure flag and HSTS work, shorten the cookie life, and enforce the content-security policy. The cookie will stay readable by page scripts, which is how the Supabase browser client works. Reviewers suggest not exposing port 3210 to the internet without a VPN meanwhile; that is management's call.
- **Status:** Requires Decision (High) - the HTTPS-ready code is LOCAL only, not deployed
- **Technical evidence:** Class A (browser check, H6) and B. Earlier audit IDs D-018, D-037, D-033. Status: Requires Decision (a fixed part exists).

### 3. VAPT-003 — Bulk-imported accounts all get the same password, written in the source code; the forced change is only a page redirect

- **Problem:** When administrators import users in bulk without a password, every account gets the same password, `<shared default password>`, which is written in the source code. The 'you must change your password' step is only a redirect in one page layout, so it does not stop someone who calls the server directly.
- **Business risk:** Anyone who knows an employee's e-mail address (they are easy to guess) can try the shared password on accounts that have never signed in. The sign-in limiter works per account, so one password can be tried on all accounts (VAPT-032).
- **Where found:** `lib/actions/admin/users.ts` lines 522, 699, 718; `app/(app)/layout.tsx` lines 37-39; `supabase/config.toml` line 182 (minimum password length 6 in the local file).
- **How we checked:** Source review of the import, the sign-in flow and the layout, and the Next.js guidance in the repository, which says a layout does not protect server actions. We did not sign in with the default password.
- **What we changed:** Only one part: a user can no longer switch off their own 'must change password' flag (VAPT-005). The shared password and the page-only enforcement are unchanged.
- **What happened after the fix:** The flag now stays on until the server clears it after a real password change (tested, VAPT-005).
- **What remains:** The default password itself, server-side enforcement, and the sign-in service's minimum length. Management must choose: random one-time passwords or invitation e-mails. Someone with admin access must check the live system for accounts that still have the default password; we did not (no production access).
- **Status:** Requires Decision (High)
- **Technical evidence:** Class B. Earlier audit IDs D-011, D-036. Original IDs VA-API-02 and VA-ADM-02 (default-password part).

### 4. VAPT-001 — The database let a technician or manager change a ticket's priority, SLA deadlines, assignee and other lifecycle fields directly

- **Problem:** The rule 'nobody, not even a manager, may change a ticket's priority' was enforced only on the screens. The database itself still accepted a direct change of priority, of the SLA deadlines, of the assignee and of other ticket fields from any technician of the group or any manager.
- **Business risk:** A technician or manager could set a ticket to low priority, move its deadline a year ahead so it never looks late, or hand it to someone else, and service-level reports would look better than reality. Changes to deadlines left no trace in the System Log.
- **Where found:** The `requests` table: policy `requests_update` and the trigger `guard_request_client_write` (migrations 157 and 163); `lib/actions/requests.ts` lines 876-883.
- **How we checked:** Reviewers read the live policy and trigger text in the isolated database. We then wrote three exploit tests (technician changes priority, manager changes priority, technician pushes a deadline a year ahead) and ran them before and after the fix on the isolated stack.
- **What we changed:** Migration 164 section 1: the database now refuses a priority change, and refuses a change of deadlines or paused time unless the status changes in the same update. The System Log now also watches the deadline columns.
- **What happened after the fix:** The three exploit calls are refused (error 42501) and the tests pass.
- **What remains:** A technician or manager can still change the assignee, description, form answers, resolved and closed times, reopen count and category through the data API. That needs column-level rights or server-only writes, a design decision. The fix is LOCAL: production still accepts the priority and deadline change.
- **Status:** Partially Fixed (High) - fixed in the LOCAL working copy only, not deployed
- **Technical evidence:** Class A (T11, three tests) for the fixed part; class B for the rest. Earlier audit IDs D-008 (partial), D-032; reconciliation R-1. Also reported as VA-DB-01, VA-TKT-01.

### 5. VAPT-023 — If the live login service allows self sign-up, any stranger holding the public key becomes an employee of the first organisation

- **Problem:** If the live sign-in service allows people to register themselves, a stranger could create an account, and a database rule would place it in the first organisation as an ordinary employee.
- **Business risk:** The stranger could then read the staff list (VAPT-019) and use other signed-in features. The only thing needed is the public key that is built into every page of the site.
- **Where found:** The trigger `handle_new_user` (migration 134); `supabase/config.toml` lines 176 and 221 (sign-up enabled in the local file); `deploy/windows/config/auth.env.example` line 51 (production template says sign-up disabled, but also turns on auto-confirm).
- **How we checked:** Source and configuration review. We cannot read the live setting because we may not touch production.
- **What we changed:** Nothing.
- **What happened after the fix:** Not applicable.
- **What remains:** An authorised administrator must read the live sign-in service setting and send us the evidence. Suggested hardening either way: make new accounts inactive until an administrator activates them.
- **Status:** Not Verified (Medium)
- **Technical evidence:** Class B. Not Verified. Earlier reconciliation R-11. Original IDs VA-DB-08, VA-API-14 (sign-up bullet).

### 6. VAPT-032 — Sign-in throttling is per account only and held in memory; a stranger can lock a named person out and one password can be tried on every account

- **Problem:** The sign-in page slows down repeated guessing on one account, but the counter lives in the server's memory and is per account. It does not slow someone trying one common password on every account, and it lets a stranger keep a named colleague locked out by sending ten wrong tries a minute. The visitor's address is probably not recorded either: it depends on a setting (`TRUSTED_PROXY_HOPS`) that appears in no environment example, and its production value was not checked.
- **Business risk:** Combined with the shared default password (VAPT-003), a password-spraying attack across the roughly 553 accounts is practical, and the log may carry no source address.
- **Where found:** `lib/actions/auth.ts` lines 20-28 and 68-72; `lib/rate-limit.ts` lines 6-15 and 49-54.
- **How we checked:** Source review. We did not run a spray test.
- **What we changed:** Limiter keys are now capped in length, and the change-password check is limited to 5 tries in 10 minutes.
- **What happened after the fix:** Code reading shows the new limits; there is no executed test.
- **What remains:** Setting `TRUSTED_PROXY_HOPS` in production, a lock-out policy (a design choice), alerting on many failed accounts from one source, and a second factor for administrators.
- **Status:** Partially Fixed (Medium) - fixed in the LOCAL working copy only, not deployed
- **Technical evidence:** Class B. Earlier audit IDs D-017, D-035. Original IDs VA-API-03, VA-TKT-18 (b, c). Status: Partially Fixed.

### 7. VAPT-006 — The database let a manager change configuration that the screens reserve for administrators (services, SLA policies, SLA configuration, many master tables)

- **Problem:** The screens let only an administrator edit services, SLA policies and SLA settings. The database allowed any manager to do the same by calling it directly. About 20 other configuration tables still allow managers.
- **Business risk:** A manager, or anyone who steals a manager login, could lengthen every SLA or rewire services for the whole company. The changes are logged, so they can be found but not prevented.
- **Where found:** Policies `services_admin`, `sla_policies_admin`, `sla_config_admin`, `field_sla_overrides_write` and about 20 more (categories, stores, OEMs, assignment, notification and alert rules, team members).
- **How we checked:** Reviewers read the policies and simulated the roles. We tested the four most important tables with a manager login before and after (T11).
- **What we changed:** Migration 164 section 6: the four tables are now writable by administrators and the platform owner only.
- **What happened after the fix:** A manager's change is refused; an administrator's still works.
- **What remains:** The other tables. The owner must decide who may edit each (the earlier audit's D-005 asks the related question about what managers may read).
- **Status:** Partially Fixed (Medium) - fixed in the LOCAL working copy only, not deployed
- **Technical evidence:** Class A (T11) for four tables; class B for the rest. Status: Partially Fixed.

### 8. VAPT-007 — Company-wide settings (business hours, holidays, priorities, any app setting) can be changed by any manager or admin through the screens, although the database says platform owner only

- **Problem:** The database says company-wide settings (business hours, holidays, priority list, any application setting) may be changed only by the platform owner. The administration screens let any manager or administrator change them, because the screens use a master key.
- **Business risk:** A manager could mark every day a holiday so no ticket ever shows as late, or rename the sender of all system e-mails to something misleading such as 'IT Security Team'. The earlier fix closed only the direct-to-database route.

- **Status:** Requires Decision (Medium)

### 9. VAPT-012 — A file attached to an internal note was stored as a normal attachment, so the requester could list and download it

- **Problem:** When a technician attached a file to an internal (staff-only) note, the file was stored as an ordinary attachment. The note was hidden from the requester, but the file was not.
- **Business risk:** A quote, a log file or a screenshot showing another customer's details could be listed and downloaded by the requester, and its name appeared in the ticket PDF and history.

- **What happened after the fix:** The requester can no longer list or download the file, and the row is flagged internal.

### 10. VAPT-011 — The first 120 characters of an internal note were sent by bell, e-mail and push to people who may not read the note (ordinary-user collaborators, @mentioned colleagues)

- **Problem:** The first 120 characters of an internal note were put into the bell, e-mail and push alert sent to the assignee and every collaborator, including collaborators who are ordinary users, and to anyone @mentioned by first name.

## 7. Items not counted as findings

**Tool-coverage gap (not a row).** Semgrep, Gitleaks, OSV-Scanner, ZAP, Nuclei and Burp are not installed. They were replaced by `npm audit`, targeted searches and the source reviews. Status: Not Verified. No secret-scanning of the repository history was done.

**Observations from the reviews that are functional defects or design notes, not security findings:**
- Avatar upload writes to an `avatars` bucket that no migration creates (`INT observation 2`); avatar upload fails unless the bucket was created by hand in production.
- The intake worker's MP4 signature check never matches, so real MP4 e-mail attachments are refused (`api/src/intake/attachmentValidate.ts:42`, INT observation 4).
- Sending a message from an intake thread is possible for any technician to arbitrary recipients through the organisation's intake mailbox (INT observation 7). By design for staff, but an open relay if an agent account is compromised.
- Phone numbers appear in intake audit log metadata (INT observation 5); the retention period is a decision.
- The permission matrix (`custom_roles`, `permission_overrides`) writes rows but nothing reads them for decisions; the screen says so. Do not rely on it as a control (ADM review).

**Areas the five reviews did not assess** (so no finding either way): production database and login-service settings; the separate intake worker in `api/` (whether it runs in production is unknown); cron routes for business rules and alerts; Gmail and Outlook OAuth internals beyond the routes; real mail delivery, DNS and TLS behaviour; the content-security policy value in effect; performance under load; the `scripts/cron-tick.mjs` and log-shipper transport. Dynamic exploitation was done only for the items marked A.
