# ISO/IEC 27001:2022 Annex A - Control Matrix for Citykart Desk (CKDesk)

Date: 2026-10-15

Status: **DRAFT for management review - internal readiness assessment, not an audit report or attestation**

## How to read this

This matrix has one row for each of the 93 Annex A controls. For each control it says what the repository shows, who should own it, what evidence an assessor would ask for, what evidence exists today, what is missing, what this assessment tested, and what we propose as the next step.

It is an internal readiness view. It is not an audit, not a certificate and not a statement of compliance. Only an accredited certification body can certify against ISO/IEC 27001.

Three rules shape every row:

1. A document or a script in the repository is **not** proof that a control works. The state is only raised to **Tested** when this assessment ran its own test on the isolated local stack, and to **Operating with evidence** only when authorised organisational records (class C) show the control working over time. No class C evidence has been supplied, so no row can be in that state.
2. The states describe the **local branch and what the repository shows**. Nothing from this assessment is deployed: production runs build 20261015-145217 (main `717e5c6`), which does **not** contain the assessment's fixes. Where a row relies on a local fix, the gap column says so.
3. Control names are written from the assessor's knowledge of the 2022 edition and objectives are short paraphrases, not quotations. **PROVISIONAL - confirm every control title and objective against the licensed standard (ISO/IEC 27001:2022 Annex A and ISO/IEC 27002:2022) before this matrix is used with an auditor.**

## Proposed scope of this matrix (PROVISIONAL - management to confirm)

The Citykart Desk service-desk application and everything it needs to run: application server 10.0.1.98, database server 10.0.0.205 (database `ckdesk`), file store on NAS 10.0.0.25, the developer PC 10.0.0.47, the admin PC that holds the server access key, the source repository, the supporting suppliers (Google Workspace mail, Meta WhatsApp, DeskTime, optional LLM, GitHub) and the people who build, run and use it. The retired server 10.0.1.12 is out of scope except for its leftover data (see A.7.14).

Controls that are run by organisation-wide functions (HR, facilities, legal) are marked **Applicable to organisation, not to CKDesk system**: CKDesk relies on them but does not provide them.

## Legend

**Evidence classes** - A verified LOCAL technical evidence (this assessment's own tests on the isolated stack) · B repository evidence (source, migrations, scripts) · C authorised organisational evidence (approved policies, access reviews, backup/restore records, training records, management approvals - **none supplied**) · D documentation-only · E missing / not verified.

**States**

| State | Meaning in this matrix |
|---|---|
| Designed | Only documented or planned, or only a minor part exists; the working element is missing or lives outside the repository. |
| Implemented | The essential element exists in the repository (class B) but this assessment did not exercise it as its main test. |
| Tested | The main technical element exists and this assessment ran a test on the isolated stack with a recorded result (the result and any open gaps are in the row). |
| Operating with evidence | Class C records show it working over time. **Not reachable today.** |
| Not implemented | Looked for; the essential element is absent. Used for system-level controls where absence in the repository is meaningful, or where the owner's own document says "not done yet". |
| Not verified | An organisational control that the repository cannot show either way. Class C evidence is required. Nothing is guessed. |
| Not applicable | Excluded with a written justification. None are excluded in this draft. |

**Test codes used in the "test performed" column** - T10 `tests/vapt/10-confidentiality-exploits.test.ts` (leak paths, before and after fix) · T11 `tests/vapt/11-integrity-exploits.test.ts` · T12 `tests/vapt/12-email-reply-participant.test.ts` (logic level) · TU `tests/unit/vapt-hardening-units.test.ts` · TB `tests/unit/approval-code-burst.test.ts` · H HTTP probes against the rebuilt audit app (logged in 02-VAPT/04-MANUAL-PENETRATION-TESTING.md) · M164 migration `20240101000164_vapt_security_hardening.sql` on the disposable database · NPM `npm audit` before and after the upgrade (VAPT-DEP-01) · GATE local isolation gate, 21 of 21 checks (01-BASELINE/02) · REV source reviews in `vapt-2026-10/work/review-*.md` (code reading, not dynamic). A test entry on a row in another state means it covered only part of the control.

**Owner roles** are placeholders. The tag **(tba)** means: **to be assigned by management** - no person is named anywhere in the repository.

**Risk (H/M/L)** is the assessor's proposal of how much the control gap matters to CKDesk. It is separate from the scored risk register.
