## 1. How to read this document

**What I compared.** Every finding in `audit-2026-10/reports/13-MASTER-DEFECT-REGISTER.md` (D-001 to D-063), the three findings added later (D-064 to D-069), REL-1, and the unnumbered Low/Info groups, against what the repository and the audit database contain TODAY. The register's own words ("Fixed") were never accepted as proof.

**Evidence I used, in this order of strength**
1. Audit-database catalogue (`pg_policy`, `pg_proc` ACLs, column privileges, triggers, indexes). This shows what the database really enforces right now.
2. Current source code, read line by line (file:line given).
3. A test in the repository that exercises the behaviour (named). I READ the tests; I did NOT run them. The last recorded passing runs are in `audit-2026-10/evidence/batch2/` (2026-10-14 09:34-09:40: unit 1186/1186, integration 401 passed / 18 skipped, remediation 162/163). That run pre-dates every later LOCAL commit (approval reminders, resolution-note rules, "Catch me up", service/priority removal, reply-sync speed-up). The single failing test in that run (`102-system-log-endpoints`, "browser events route mirrors a browser error...") was changed in commit `d63b4d2` but I found no recorded re-run.

**Classification used (exactly the seven labels requested)**
- `Fixed and independently verified` = the exploit the audit described is closed in the code/database I read AND I found a test (or a catalogue fact) that exercises it, AND I found no way round it. If the fix covers only part of the finding I put `[PARTIAL]` at the start of the note. If I found a smaller, different weakness next to it, the note points to a residual item `R-n` in section 4.
- `Fix present but not retested` = the fix is in the code, but I found no test that proves it.
- `Still vulnerable` = I found, in the code or catalogue, a path by which the original problem can still be reached.
- `Requires business decision` = nothing technical is blocking; the owner has to choose (or the item is a deployment setting).
- `Superseded by newer implementation`, `Not reproducible`, `Cannot verify with available evidence` as named.

**Environment facts that matter**
- The audit database holds the objects of migrations 156-163 (system_log, approval_email_codes, request_status_transition_allowed, the index from 162 ...), but its bookkeeping table `supabase_migrations.schema_migrations` lists versions only up to 155. The migrations were applied by hand. I treated the catalogue, not the table, as the truth.
- Per the project notes the audit batches (migrations 156-163) went live on 2026-10-14. I cannot and did not check production. Anything that depends on a production setting is marked `Cannot verify` or `Requires business decision`.
- A sibling reviewer's files in `vapt-2026-10/work/review-*.md` overlap with some points below. I re-checked each overlapping point in the code myself before using it; where I could not, I say so.
